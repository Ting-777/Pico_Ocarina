# 配置化方案：MIDI → 主旋律文件 → Pico演奏

## 已明确的职责边界

用户要的是两步流水线：

1. **电脑端：MIDI → 主旋律配置文件。** 可以由固定程序生成，也可以由AI辅助选择轨道/片段后生成。
2. **Pico固件内部：读取配置文件 → 校验 → 按时间把音高映射成手柄按键/摇杆 → 发送USB报告。** 换曲只上传文件，不重新编译UF2，不再把音符数组写进源码。

第二步必须是固件功能。不能把“电脑生成C++数组再编译UF2”作为完成配置化的结果；也不能让Windows在演奏时不断实时发送每个音。Pico保存文件后，应能离开电脑、接Switch独立演奏。

**当前v1.1仍是静态歌曲数组。本文是后续实现要求，并不表示读取配置/上传/持久存储已经实现。**

## 第一步推荐固定程序，AI负责辅助

MIDI中的音高、起音、时长和tempo map本来就是确定数据，固定程序更容易逐音核验，避免此前段落/八度选择错误。最小工具只需要命令行，不必先做GUI。

- 固定程序解析MIDI，列出轨道并让用户选主旋律轨、片段、复音策略、整体移调和速度。
- AI可帮助判断哪条轨像主旋律，或在复杂多声部中建议选择；不应凭听感改八度。
- 若直接让AI输出配置，也必须通过同一份schema和语义校验，且能从该文件生成试听。
- 试听MIDI与设备文件使用同一份演奏时间线；不要分别推导，以免听到的和板子发送的不一致。

本项目已提供完整/短版的**配置草案样例**，可以先作为固件开发输入，所以不必先实现完通用MIDI导入器才开始做第二步。

## 配置文件保存音符，不保存源码或原始USB包

文件包含最终演奏音高与绝对时间，形如：

```json
{
  "format": "pico-ocarina-melody",
  "schema_version": 1,
  "title": "Example",
  "fingering_profile": "oot-user-image-reference-v1",
  "countdown_us": 3000000,
  "duration_us": 1000000,
  "notes": [
    [0, 341356, 81],
    [381356, 468475, 81],
    [508475, 722712, 81]
  ]
}
```

每个音是`[开始微秒, 松键微秒, 演奏MIDI音高]`，时间相对歌曲起点，单位全部为微秒。81是A5，不是简谱数字，也不是某个手柄按钮。

详细契约见 [配置文件格式](MELODY_FILE_FORMAT.md) 与 `schemas/melody-v1.schema.json`。该v1契约是开发目标，尚无设备端实现。

关键约定：

- 选轨、复音化单音、整体移调、速度变换在第一步完成；文件里已经是最终音高与时间。
- 固件不再次移调、不再次缩放速度、不额外再扣一次40ms。超出音域/缺指法直接报错，不能自动折八度。
- 音高→按键/左摇杆/十字键的转换在板子里完成，固件内提供受校验的19音指法profile。
- `metadata`仅作来源审计；例如其中记录`transpose_semitones: 5`，不表示板子还要再加5。
- 同一文件驱动电脑试听与Pico演奏。USB轮询和游戏帧仍可能引入实际采样量化，需要实测记录。

## 固件必须实现的第二步

| 模块 | 必需行为 |
|---|---|
| 文件接收 | 从Windows接收完整配置，限制长度，报告错误 |
| 文件校验 | 检查格式版本、profile、音符数量、音高、起止时间、顺序、最短释放间隔和总时长 |
| 持久保存 | 保存到Pico Flash；重新断电上电后仍可读取；坏文件不能替换上一份可用歌曲 |
| 加载 | 将已校验文件转换为有上限的内存事件表；不需要在板子上解析MIDI |
| 指法 | 根据音高查内置profile，独立设置按钮位、左摇杆和十字键；补齐图中的19个音 |
| 播放 | 绝对时间非阻塞调度、倒数、休止、单次播放、随时停止、结束后中立状态 |
| 状态 | 能回读已保存歌曲的版本、音数、时长、摘要及错误码 |

首先支持固定的`oot-user-image-reference-v1`内置profile；完整参考在`profiles/oot_user_image_reference.json`（19音、26按法）。MVP每个音选一个确定按法；让用户另行上传/修改指法表可作为后续功能，不阻塞换曲。

## 上传与板内“读文件”如何落地

Pico不能直接读取Windows上的某个路径。需要把`melody.json`的字节传进板子，再保存在Flash。保存后固件从Flash加载；不要求接SD卡。

推荐先实现Windows上的小型上传CLI，例如设计中的：

    python upload_melody.py melody.json --port COM5

这只是目标用法，脚本目前还不存在。MVP可采用**独立USB配置模式 + CDC串口协议**，演奏模式保持现有Pro HID描述符。不要未经实测就把CDC加入常驻复合设备并宣称Switch兼容。

上传至少区分开始、分块数据、验证、提交、状态和中止，并包含长度及CRC/摘要。线上的精确命令和进入配置模式的手势待实现时确定；现有BOOTSEL短按播放、长按1秒L+R、插电前按住进ROM刷机的行为不能被不加说明地覆盖。

拖文件到虚拟磁盘/做GUI都可后做。MVP只要从Windows成功传文件、保存、拔掉电脑再接Switch播放，就满足核心链路。

## 容量与存储要求

v1草案上限：文件64KiB、4096个单音事件、歌曲60分钟、倒数0–10秒。当前完整版只有572个事件，远小于这些目标上限。

这些是需要由实现验证的设计上限，不是已经测过的固件能力。建议采用有界流式解析，避免大型JSON DOM和多份事件表同时占用RAM；构建时检查实际堆栈/内存预算。使用明确的Flash歌曲分区、双槽或其他原子提交方式，带schema版本、长度、CRC和有效标志。

Flash写入只在停止播放并协调好USB/中断/BOOTSEL采样时进行；当前BOOTSEL读取会短暂释放Flash CS。保持单核结构，除非另外解决另一核心的Flash访问。没有可用文件时保持中立，并明确提示状态，不自动演奏垃圾数据。

## 开发顺序：先完成板内播放器，再完善第一步

| 顺序 | 任务 | 验收 |
|---|---|---|
| 1 | 固定文件契约；用已有样例实现固件的有界解析器和`LoadedSong`接口 | 样例可加载；版本/越界/乱序/重叠/缺指法明确拒绝；旧歌曲不因加载失败被破坏 |
| 2 | 将播放器从`SONG[]`改为读取`LoadedSong`；内置19音profile | 同一文件的native输出与原示例一致；第一遍低尾句与后续高音变体保留；开始/停止/中立正确 |
| 3 | 设备Flash持久化、独立配置模式与Windows上传CLI | 同一UF2接收两首不同文件，换曲无需编译；断电保留；坏包/掉电回退；无需电脑陪同播放 |
| 4 | 真机验证有线Pro识别及19音指法 | 逐项记录主机、玩家分配、音高、修饰、停止及完整演奏结果 |
| 5 | 通用MIDI导入程序 | 支持选轨、片段、tempo map、复音策略、统一移调；试听与配置逐音一致 |
| 6 | AI辅助/Windows GUI/多曲槽等体验增强 | 第一、二步仍通过稳定文件契约解耦，不把AI作为板子运行依赖 |

阶段1–3是固件第二步的核心交付。不要先投入大型GUI，也不要停留在“每次换曲重新生成头文件编译”的过渡方案。
